# QQL SDKs vs Official Qdrant SDKs — Head-to-Head Benchmark

Reproducible, parity-checked comparison of the QQL SDKs (`pyqql`, `nqql`, `qql`)
against the official Qdrant SDKs (`qdrant-client` Python,
`@qdrant/js-client-rest`, `qdrant-client` Rust) on the same data, same server,
same scenario set — three language pairs, REST-vs-REST (Python, Node) and
gRPC-vs-gRPC (Rust).

**Everything in this folder is regenerable from scratch**: a deterministic
corpus generator, a GPU embedding pipeline with checksummed artifacts, and one
harness per language that runs both contenders and asserts result parity
before it reports a single timing number.

This is **run 5** — ingest on all three legs goes through the bulk
`upsert_many` / `upsertMany` helpers (one `:rows` template prepared once,
no hand-rolled batch loops). Run 1 (pre-fix API shape) is preserved
in `results/run1/`; §"What moved" quantifies every leg of the journey.

---

## TL;DR (Qdrant 1.19.1, GTX 1060 host, 2026-09-08, run 5 — bulk `upsert_many` adoption)

| | Python (REST) | Node (REST) | Rust (gRPC) |
|---|---|---|---|
| Read scenarios won by qql | **10 / 10** | **10 / 10** | 3 / 10 (count_legal 1.04x, facet 1.02x, count_berlin 1.01x) |
| Best qql advantage | **3.6x** (count), 2.9x (facet), 2.0x (sparse) | **5.9x** (count), 4.3x (facet), 3.1x (sparse) | 1.04x (count_legal) |
| Ingest (10k pts, wait=false) | **0.44x — 2.3x faster than official** | **0.81x — faster than official** | 2.04x slower (was 4.5x pre-fix) |
| Cold import/require | **39x faster** (29.5 vs 1140 ms) | 2.9x faster (35 vs 100 ms) | n/a (compiled) |
| Application LOC | 0.86x | 0.81x | **0.70x** |
| Result parity | exact / ANN-equivalent | exact / ANN-equivalent | exact / ANN-equivalent |

The headline pattern: **QQL wins the read path on the dynamic-language
transports** (the parse→plan→route pipeline plus payload extraction beat the
official SDKs' pydantic/typed-object response layer), while the **official
Rust gRPC client is faster on raw reads** (protobuf-in / protobuf-out with no
intermediate AST). After the 0.4.0 write-path fixes, the Rust ingest gap
narrowed from 4.5x to ~2.0x and scroll parity returned to exact 1.0.

Every qql advantage above was measured **after parity checks passed** — the
two contenders return the same points, same scores (≤ 2e-5 difference from
f32-vs-text float rounding), same facet counts, same filtered counts.

## Methodology

### Data (deterministic, seeded)

Two domains, generated by `pipeline/gen_corpus.py` (seed 42 — byte-identical
on any machine, no network):

| collection | docs | vectors per point | payloads |
|---|---:|---|---|
| `vsq_berlin_*` | 8,000 | dense 384 + bm25 sparse | name, description, district, price, rating, guests, amenities |
| `vsq_legal_*` | 2,000 | dense 384 + **colbert 128×~63 tokens** + bm25 sparse | case_ref, title, summary, court, year, cited_by, tags |

The legal collection is the serialization stress test: a ColBERT point
carries ~55–90 token vectors (~150 KB), which amplifies every SDK's
encoding/decoding cost.

### Embeddings (precomputed once, on the GPU)

`pipeline/embed.py` runs fastembed **once** on the GPU and writes flat f32 /
JSON artifacts with a SHA256 manifest (`data/manifest.json`). **All six
clients then consume byte-identical vectors** — embedding inference is
deliberately decoupled from the SDK comparison (none of the official SDKs
embed, and fastembed-js is archived; see caveats). Fixed query vectors
(dense, ColBERT, bm25) are precomputed the same way, so JS/Rust need no
embedder at all.

### Collections & ingestion

Each contender builds its **own** collection (`vsq_<dom>_official`,
`vsq_<dom>_qql`) with the same config (named dense+sparse+multivector,
`modifier=idf` on bm25, colbert HNSW `m=0`, payload indexes). Ingestion uses
each SDK's idiomatic batched upsert (`wait=false` on both — qql upserts now
*support* `WAIT true`, measured with it for update/delete): each qql batch
binds its 100 vectors as **statement parameters** (`vector: :v0 … :v99`), so
no vector text is parsed. An **untimed durability barrier** (poll
`points_count`) precedes any read. A raw-REST probe after ingest compares one
point from each collection — payload and all vectors must be identical.

### Timing

- Reads: warmup rep untimed, then median-of-`reps` × `iters` (defaults 5×25),
  ops/s + p50/p95. Both contenders run interleaved per scenario.
- Ingest: single timed pass per side (submission throughput).
- Cold import/require: median of 5 fresh processes.

### Parity protocol (the core of the harness)

No timing is reported until results are compared:

| scenario | requirement |
|---|---|
| count, facet | exact match |
| query_sparse (bm25, idf) | exact top-10 ids, scores ≤ 2e-5 |
| query_dense / query_colbert | exact top-10 + scores (0.0 diff observed) |
| scroll pages | exact id sequence (1.0 after the exclusive-cursor fix) |
| query_hybrid (RRF) | compared against a **self-consistency baseline**: the official client is queried twice and its own run-to-run jaccard recorded, because Qdrant's RRF tie-breaking at equal scores is nondeterministic *within one SDK*. qql-vs-official must be within that baseline. |
| update payload, delete by filter | exact (facet map / count after), both sides `wait=true` |

Rust gRPC context: the official client remains the fastest bulk-ingest and
raw-read path (protobuf-in / protobuf-out, no intermediate AST). Ingest is one
`upsert_many` call (payload and vectors as data, template prepared once,
chunks moved — never cloned — through the point-splice path) — 0.815 s vs
1.666 s (2.04x). The residue is peak memory (the full row `Vec` stays alive
during ingest, where the old code built per-batch) plus per-point value
conversion and gRPC dispatch — not statement text. Vector reads stay at
0.56–0.98x — the parse→plan→normalize pipeline cost; `count` / `facet` are at
0.96–1.04x (three read wins this run).

### Native BM25 wire-parity proof (Rust leg)

The Rust harness additionally proves that qql's **built-in** BM25 (no HTTP
embedder, no precomputed vectors — `QUERY TEXT` resolution) is wire-compatible
with fastembed's `Qdrant/bm25`:

| check | result |
|---|---|
| query token ids (murmur3-32) vs pipeline artifacts | **match** (fastembed returns token order, qql sorts — ordering only) |
| document tf-saturation weights vs ingested artifacts (doc 0) | **byte-identical** (25/25 terms, 0 value diffs) |
| qql native-BM25 query vs official with precomputed vector | top-10 identical (uniform query-weight scale, same ranking) |

## What moved (pre-fix baseline → current, qql side)

The 0.4.0 fixes (vector-parameterized upserts, `F32Array` zero-copy binding,
pre-planned prepared statements, exclusive scroll cursors, `WAIT` on
mutations, typed gRPC response hits) were adopted by the harness and
re-measured:

| change | measured effect |
|---|---|
| vector params on upsert + `F32Array` (Rust) | **rust ingest 3.78 s → 1.53 s (−60%)**; gap to official 4.5x → 1.9x |
| pre-planned prepared statements (Rust) | rust `prepared_rerun` 183 → 211 ops/s (+15%) |
| exclusive `AFTER` cursor | scroll parity 0.997 → **exact 1.0** on all legs |
| new bind/normalize paths (Python) | sparse +13%, count_legal +12%, facet +9%, dense +7% ops/s; ingest −7% |
| `WAIT true` on writes | both sides now settle identically; parity on update/delete unchanged |
| **node ingest via params (regression)** | nqql ingest 9.8 s → 11.8 s (+20%, reproduced twice): NAPI per-element JS-array extraction costs more than the previous fast string-literal builder. Reads unaffected (flat across reruns). Backlog: bulk/zero-copy JS array → `F32Array` transfer. |
| noise exclusions | one node run showed −10…−21% on non-vector reads; a full rerun restored run-1 levels — treated as environment noise, not recorded |
| **typed-array / numpy bind fast paths (run 3)** | **python ingest 15.9 s → 8.34 s (0.99x vs official — gap eliminated)**; **node ingest 11.8 s → 8.26 s (0.92x — faster than the official client)**. dense = `Float32Array` view / numpy row; bm25 values typed; colbert = flat `{data, dim: 128}` — all one memcpy via `F32Array` |
| net ingest after run 3 | **python 0.99x, node 0.92x, rust 1.88x** vs official — the former 2.0–4.5x ingest deficit is closed on the FFI legs; rust's residue is payload/statement construction, not vector encoding |
| **whole-point `:rows` params + prepared ingest (run 4)** | payload and vectors become **data, not statement text**; template prepared once, schema resolved once. **python ingest 8.34 s → 3.69 s (0.45x — 2.2x faster than the official client)**; node 8.26 → 8.82 s (0.96x — the async napi statement boundary dominates, see findings); rust 1.50 → 1.62 s with official drifting 0.79 → 0.85 s (ratio ~1.9x, unchanged). Adoption also caught and fixed a runtime bug (blind `vectors.take()` dropped named vectors on the fast path — see findings #14) |
| **bulk `upsert_many` helpers, no hand-rolled batch loops (run 5)** | one call per collection — prepare-once, move-not-clone chunking. **python holds 0.44x (3.48 s)**; **node 8.82 s → 7.11 s (0.81x — faster than official, best ever)** after disproving the serde fear (the 141 saved per-batch RPC round-trips dwarf conversion cost, measured release-vs-release); rust 1.97 s → 1.67 s (2.04x) after fixing a chunk-clone tax the adoption exposed (`chunks().to_vec()` deep-cloned every point). Harness scenario code falls on every leg (py 133→126, node 138→123, rust 326→293 lines) |

Remaining qql ingest gap (2.0x py / 1.3x node / 1.9x rust) is now dominated by
ColBERT param conversion (nested per-token lists) and payload encoding — not
by vector text parsing, which is gone.

---

Line counts understate the real difference — the dimensions that don't show
up as lines:

1. **The official SDKs cannot express the benchmark's queries without an
   out-of-band embedding pipeline.** Every dense/ColBERT/bm25 query vector and
   every document vector had to be produced by `pipeline/embed.py` first.
   QQL resolves `TEXT` and (in the Rust runtime) native BM25 in-process — the
   sparse path needs **zero embedding infrastructure**.
2. **One statement instead of a request-builder graph.** QQL hybrid is 4 lines
   of SQL; the official Rust client needs a `QueryPointsBuilder` +
   two `PrefetchQueryBuilder`s + protobuf vector plumbing (~60 lines).
3. **Typed, located errors.** Every QQL failure carries an error code and the
   source span that caused it (`QQL-BIND-MISSING-PARAM` at 21:9); official SDK
   errors surface as server 400s or pydantic validation traces.
4. **Response normalization.** qql/`nqql` hits are plain dicts with `id`,
   `score`, `payload`; the official Python client returns `ScoredPoint`
   objects whose payloads must be unpacked (`p.payload[...]`, protobuf `Value`
   unwrapping in Rust before anything is JSON-serializable).

## Findings (surfaced by the parity harness)

Behavioral differences the benchmark had to accommodate. All qql-side items
below were **fixed in the 0.4.0 dev tree and re-measured in run 2**; they are
kept here with their evidence because they document *why* the harness looks
the way it does.

**Fixed on the qql side (verified in run 2):**

1. ~~UPSERT vector parameters unsupported~~ → `vector: :v` binds dicts of
   dense/sparse/multivector params (run 2 uses it for every ingest batch).
2. ~~Textual re-parse of bound sparse/multivector params fails~~ →
   `parse_query_input` accepts `{indices, values}` literals; prepared
   statements pre-plan vector templates.
3. ~~`SCROLL AFTER` inclusive of the cursor~~ → exclusive for integer and
   UUID ids; scroll parity restored to exact 1.0.
4. ~~`QUERY POINTS WITH VECTOR` drops vectors; stringified ids/scores~~ →
   `SearchHit.vector` populated on REST + gRPC; id/score typing unified.
5. ~~Facet index-readiness race surfaced as opaque 400~~ → named
   `QQL-BACKEND-INDEX-NOT-READY` (plus COLLECTION-NOT-FOUND,
   DIMENSION-MISMATCH, STRICT-MODE, AUTH mappings) on both transports.
6. ~~No `WAIT` on mutations~~ → `WAIT true/false` on UPSERT / DELETE / UPDATE
   / CLEAR PAYLOAD / CREATE INDEX.

**Qdrant-side observations (for the Qdrant team):**

7. **`qdrant_client` default sparse params omit `modifier=idf`**, while
   QQL's `sparse SPARSE` column defaults to idf. With fastembed `Qdrant/bm25`
   vectors and no modifier, scores are not BM25 (Δ on this corpus: ~10.5 vs
   ~21–24) and rankings differ. Qdrant's own docs recommend idf for bm25 —
   but the client default silently produces the wrong ranking.
8. **RRF tie-breaking is nondeterministic at equal scores even within one
   client** (positions 5/6 swap between two identical calls). Benchmarks of
   hybrid fusion need the self-consistency baseline this harness records;
   single-shot fusion comparisons will flake.
9. **Python client cold import is ~1.1 s** (pydantic model graph) vs 29.5 ms
   for pyqql — matters for serverless/CLI usage.

**Fixed after run 2 (typed-array / flat-multivector bind fast paths, run 3):**

10. ~~nqql ingest via vector params regressed ~20%~~ → JS `Float32Array` /
    `Int32Array` params convert to `F32Array` in one memcpy on the sync bind
    surface; **node ingest 11.8 s → 8.26 s (0.92x vs official)**.
11. ~~ColBERT ingest conversion dominates the Python ingest gap~~ → flat
    `{data, dim: 128}` multivector convention + numpy memoryview fast path;
    **python ingest 15.9 s → 8.34 s (0.99x vs official)**.

**Fixed in run 5 (bulk `upsert_many` adoption):**

16. ~~Node bulk ingest needs the bind loop~~ → disproven by measurement:
    `upsertMany` (plain arrays over the serde boundary) beats the typed-array
    bind loop 8.47 s → 7.11 s release-vs-release — the ~140 saved per-batch
    RPC round-trips and per-batch planning dwarf conversion cost. The old
    "`upsertMany` would regress Node" fear was wrong; the 23 s scare during
    adoption was a debug (non-release) NAPI binary, not the API shape.
    Always benchmark the vendored **release** build (`npm run build`).
17. ~~`upsert_many` chunk-clone tax~~ → `chunks().to_vec()` deep-cloned
    every point per chunk; now moved (`into_iter` + `take`), 1.97 s → 1.67 s
    on the Rust leg.

**Open qql backlog:**

12. Rust ingest residue (2.04x) — peak live-set memory (the full row `Vec`
    stays alive during `upsert_many`, vs per-batch construction before) plus
    per-point value conversion + gRPC dispatch. For million-row ingests,
    chunk the *calls*; `upsert_many` chunks transport, not memory.
13. Rust vector reads (0.56–0.98x) — the parse→plan→normalize pipeline; the
    typed-result fast path (see #15) is the next lever.
14. ~~Prepared `:rows` dropped named vectors~~ → **fixed during run-4
    adoption**: blind `vectors.take()` in the unnamed→named mapping removed
    Named vectors when the pattern didn't match; the fast path then sent
    vector-less points ("Expected some vectors"). Regression-tested
    (named dense+sparse preserved).
15. Typed Rust result accessors — `report.hits()/facet()/count()` like
    node/python already expose; removes the SearchHit→JSON→user double hop
    on the gRPC leg (queued; small).

## Reproduce

```bash
# 1. environment (GPU embedding; see caveats for CPU fallback)
python3 -m venv .venv && .venv/bin/pip install "fastembed" "onnxruntime-gpu==1.26.0" qdrant-client numpy
.venv/bin/pip install vendor/wheels/pyqql-0.4.0-*.whl        # or: pip install pyqql==0.4.0
cd node && npm install && cd ..
# nqql MUST be the release build for timing (debug is ~2x slower across the
# board): (cd crates/nqql && npm run build) then refresh node/nqql/ copies
cd rust && cargo build --release && cd ..                    # qql deps via path until release

# 2. data + vectors (deterministic, seeded; GPU)
.venv/bin/python pipeline/gen_corpus.py
.venv/bin/python pipeline/embed.py

# 3. the three legs (Qdrant 1.19.1 on localhost:6333 + :6334)
.venv/bin/python python/bench.py            --reps 5 --iters 25
node node/bench.js                          --reps 5 --iters 25
./rust/target/release/vs-qdrant-bench       --reps 5 --iters 25

# 4. report tables + LOC (count first: the renderer reads loc.json)
.venv/bin/python common/count_loc.py
.venv/bin/python common/render_results.py > results/tables.md
```

Collections are dropped and rebuilt on every run (`vsq_berlin_*`,
`vsq_legal_*`) — nothing else on the server is touched.

## Caveats (read before quoting numbers)

1. **Embedding is precomputed, not in-path.** The comparison measures SDK +
   serialization overhead. qql's `TEXT`-param embedding resolution is a DX
   advantage that does not appear in the latency tables (it can't be measured
   fairly: the official JS/Rust SDKs have no embedder at all).
2. **Single node, localhost.** Numbers include no network jitter beyond
   loopback; a real deployment adds RTT, which shrinks relative client-side
   differences.
3. **One machine.** Absolute numbers are hardware-specific; the ratios and
   parity results are the portable claims.
4. **wait=false ingest.** Both sides submit without waiting for consensus; a
   durability barrier precedes all reads, and the write scenarios run with
   `wait=true` on both sides. Ingest numbers are submission throughput, not
   settled-write throughput.
5. **ColBERT queries hit an exact-scan (HNSW m=0) vector field** — ~24 ms
   p50 dominated by server compute, which is why all three language pairs
   converge to ~1.0x there.
6. **Rust leg is gRPC-vs-gRPC** (the official Rust client is gRPC-only); the
   Python/Node legs are REST-vs-REST (their idiomatic default). Cross-language
   absolute comparisons are therefore not valid — only within-pair ratios.
7. pyqql 0.4.0 / nqql 0.4.0 / qql 0.4.0 were vendored from local builds
   (`vendor/wheels/`, `node/nqql/`, path deps) — switch to registry packages
   once published for a fully network-only repro.
